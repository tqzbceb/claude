# Discord 层级命名约定（dcwatch 定稿版）

> 这一份是**全项目唯一口径**：代码里的字段名、界面上的文案、README、以及所有发给大模型的
> 提示词，一律按这里说话。用户 2026-08-01 让 Gemini 起草了 5 层结构，审过 —— **主干是对的**，
> 本文在它基础上做了四点修订（见每层的「dcwatch 补充」和文末「为什么要改这四点」）。
>
> 谁要读：① 接手的 AI（写规则、写文案、写提示词之前）；② 大模型（`presets/教模型写规则.json`
> 会把本文的精简版塞进系统提示词）；③ 用户自己想搞清「频道」和「帖子」到底差在哪儿的时候。

## 主干：1–5 层

### 第 1 层 · 服务器（Server / Guild）
最顶层的容器，装着所有分类、频道和成员。
- Discord 官方界面叫 **服务器**，API 里叫 **guild**。两个词是同一个东西，**说人话时统一叫「服务器」**。
- dcwatch 字段：`guild_id` / `guild_name`。

### 第 2 层 · 分类分组（Category）
用来归类频道的文件夹，本身不能发消息。
- 在数据上它是频道的 `parent_id` 之一。
- **dcwatch 补充**：分类不进 dcwatch 的规则条件。用户想「盯一整个分类」只能把里面的频道逐个填进去
  （Discord 的旁听 DOM 里拿不到可靠的分类归属）。界面上别提供「按分类监听」的入口。

### 第 3 层 · 频道（Channel）
挂在服务器或分类下的**固定**节点。dcwatch 认四种：

| 类型 | 界面图标 | 能不能直接发消息 | dcwatch 怎么看 |
|---|---|---|---|
| 文字频道 Text | `#` | 能 | 消息来源；也可以在里面开讨论串（第 4 层） |
| 论坛频道 Forum | 论坛图标 / 显示「X 个新帖」 | **不能** | 只承载第 4 层的帖子；「有人开新帖」在这里触发 |
| 公告频道 Announcement | `#` 带小喇叭角标 | 能（一般只有管理员能发） | **行为同文字频道**，不单独区分 |
| 语音频道 Voice | 小喇叭 | 有**文字聊天区** | 里面的文字消息按普通消息对待 |

- **dcwatch 补充 1**：语音频道后来也有文字聊天区了，所以**别写「语音频道无须打字」**这种话。
  dcwatch 不碰音频流，只处理文字消息 —— 语音频道的文字聊天区对它来说就是个文字频道。
- **dcwatch 补充 2**：公告频道是独立类型，但对 dcwatch 完全等价于文字频道，不必在界面上多列一项。

### 第 4 层 · 帖子 / 讨论串（Thread）
**动态**子节点，会自动归档、会消失，不是常驻结构。这是最容易搞混的一层：

```
论坛频道里点开的「帖子」  ≡  文字频道里开的「讨论串」  ≡  左侧列表里缩进挂在父频道下面的那一条
```

三种说法在 Discord 底层是**同一个 Thread 接口**。dcwatch 里统一叫「**帖子**」，
字段是 `is_thread=1` + `parent_id` 指向第 3 层。

- 界面特征：用户「关注 / 参与 / 点开」某个帖子后，它才会以**缩进**形式出现在左侧频道列表里。
- **dcwatch 补充 3（重要，直接决定用户能不能收到消息）**：
  **浏览器旁听模式下，没点开的帖子读不到帖内消息** —— 网页 DOM 里根本没有那些消息。
  这时 dcwatch 只能看到「有新帖 + 帖子标题」。想读帖内消息，那个帖子的标签页必须是打开的。
  （这就是 BACKLOG C2「自动点开新帖」要解决的事，还没做。）

### 第 5 层 · 消息（Message）
最终的文本 / 图片 / 附件，叶子节点。
- 只能挂在**第 3 层的文字类频道**或**第 4 层的帖子**里面。
- dcwatch 字段：`msg_id` / `author_id` / `author` / `content` / `ts`。
  图片、贴纸、自定义表情在上报时会被翻成 `[图片]` / `[贴纸 xx]` / `:emoji:`。

## 第 0 类 · 私信（DM）—— 树外

**dcwatch 补充 4**：私信和群组私信**不在这棵树里**，它没有服务器、没有分类。
规则里 `dm` 默认是 **False**，也就是**私信默认不命中**。这不是 bug，是默认值。
想收私信的话，规则里那个「私信也算」得自己勾上。

## 与 dcwatch 数据模型的对应（写代码 / 写规则时按这个来）

| 约定层级 | 库里长什么样 | 规则里怎么填 |
|---|---|---|
| 1 服务器 | `messages.guild_id` | 规则没有「按服务器」条件，靠频道 ID 间接限定 |
| 2 分类 | 不存 | 不支持 |
| 3 频道 | 一条 channel，`is_thread=0` | 「频道」条件填它的 ID |
| 4 帖子 | **也是一条 channel**，`is_thread=1` + `parent_id` | 「频道」条件**填第 3 层或第 4 层的 ID 都行** |
| 5 消息 | `messages` 表一行 | 关键词 / 作者 / 长度等条件作用在这一层 |

两条铁律：

1. **规则的「频道」条件填父频道（第 3 层）的 ID 时，它下面的帖子（第 4 层）算不算命中？**
   算 —— 匹配时会把 `parent_id` 也拿去比。填帖子自己的 ID 则只盯那一个帖子。
2. **「有人开新帖」这个 kind 只在第 3 层的论坛 / 文字频道上触发**，填帖子自己的 ID 永远不会响
   （帖子里不会再开帖）。规则第 0 项那两个勾（「有人发消息」/「有人开新帖」）是**独立**的，
   只勾后者时频道里聊翻天也不会响 —— 用户真踩过。

## 给大模型的一段话（提示词里就抄这段，别自由发挥）

> Discord 的结构是：服务器 > 分类 > 频道 > 帖子 > 消息。
> 「频道」是常驻的（文字 `#` / 论坛 / 公告 / 语音），「帖子」是频道里动态开出来的子节点
> （论坛里叫帖子、文字频道里叫讨论串、左侧列表里是缩进的那一条，底层是同一个东西）。
> 论坛频道本身不能发消息，消息只存在于文字类频道和帖子里面。
> 写 dcwatch 规则时：频道条件填频道 ID 或帖子 ID 都合法（填频道 ID 会连它下面的帖子一起盯）；
> 「有人开新帖」只对频道成立，对帖子不成立；私信不在这棵树里，规则默认不管私信。

## 为什么要改这四点（审 Gemini 稿的记录，2026-08-01）

1. **加了私信是「树外第 0 类」**：原稿只有 1–5 层，看完会以为「所有消息都在服务器里」，
   于是想不明白 dcwatch 为什么有个 `dm` 开关。
2. **删掉「语音频道无须打字发帖」**：Discord 已经给语音频道加了文字聊天区，
   写死这句话会让模型断言「语音频道没有消息」，然后拒绝给用户建规则。
3. **补了公告频道**：原稿只列三种频道类型，遇到公告频道模型会归错类。
   （但对 dcwatch 它等价于文字频道，所以只在文档里说明，不进代码分支。）
4. **写死了第 4 层跟 dcwatch 数据模型的对应关系**：原稿只讲 Discord 侧，
   没讲「帖子在 dcwatch 库里也是一条 channel」，模型据此写规则时会去编一个不存在的
   `thread_id` 字段。这一条是四点里最值钱的。

**这份约定覆盖得住用户的使用场景吗？** 覆盖住了 —— 他盯的是白嫖 API key 的社群，
形态就三种：① 文字频道里有人直接贴 key（第 3 层 + 第 5 层）；② 论坛频道里有人开新帖发 key
（第 3 层触发「开新帖」+ 第 4 层的帖内消息）；③ 有人在帖子里追加 key（第 4 层 + 第 5 层）。
三种都在这棵树里，且都能用「频道 ID + kinds」两个条件表达出来。
唯一表达不出来的是「盯一整个分类」（第 2 层），旁听模式下拿不到分类归属，只能逐个填频道。
